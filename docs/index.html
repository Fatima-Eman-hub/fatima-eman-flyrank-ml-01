Which Pages Should Be Reviewed First? A Client-Grouped Content Refresh Scoring Model

Fatima Eman · FlyRank ML Engineering Internship, Capstone · July–August 2026

Abstract

Content teams reviewing hundreds of pages need a way to decide which ones to look at first, but a simple hand-written rule turns out to be an unreliable guide. Using FlyRank's pseudonymized search-performance warehouse (78.8M daily rows across 70 clients), I built and validated a page-level scoring model that predicts whether a page's traffic will decline in the following month, using only observable pre-decision signals (impressions, search position, content age, and analytics availability). Under an honest, client-grouped validation split — which prevents a model from learning client-specific shortcuts — a random forest model reached a Precision@50 of 0.700, clearly ahead of the hand-written baseline rule (0.500) and the base rate (0.578); a naive random split inflated the same model's apparent score to 0.900, demonstrating exactly the kind of leakage this validation design was built to catch. This is a decision-support tool for prioritizing manual review, not a causal claim that refreshing a page will recover its traffic.

Introduction & Problem Statement

FlyRank's content teams are responsible for reviewing large inventories of client pages with limited time. In practice, this means picking a handful of pages to look at first out of hundreds or thousands. The existing approach relies on hand-written rules — for example, flagging a page as worth reviewing if it is both stale (not updated in 180+ days) and still visible (500+ impressions). This works as a starting point, but it is a coarse filter: it can only combine a couple of signals with a hard cutoff, and it cannot weigh position, traffic, and freshness together the way a learned model can.

The decision this work supports is simple to state and hard to get right: given everything knowable about a page today, which pages are worth a human's limited review time first? Getting this wrong has a real, if modest, cost — time spent reviewing a page that didn't need it, while a genuinely declining page waits longer.

Data

This work uses the FlyRank ML Internship warehouse release (build v20260703), a pseudonymized snapshot of real client search-performance data, hosted on Hugging Face. Two tables were used:

  • fact_content_daily_performance — 78,835,655 rows, grain of report_date × client × content item, spanning 2025-01-27 to 2026-06-30.
  • dim_content — 519,606 rows, one per pseudonymized content item, providing content creation dates.

Features were built from March 2026 (a mid-panel month, deliberately not the final month in the release, which is reserved to avoid natural outcome-window bias). The label was built from April 2026 impressions, so that every feature is knowable strictly before the outcome it predicts.

Excluded, and why: FlyRank's own product decision flags (health_score, priority_score, action_type, refresh_tier) are never used as features, per the internship's observable-only data discipline — including them would let the model re-learn the existing rule rather than find new signal. Raw client names, domains, URLs, and query text are never referenced anywhere in this work or its outputs.

Methodology

Assumptions. The core assumption is that a page's near-term trajectory (declining vs. not) is predictable from its own recent observable signals, and that this relationship is reasonably stable across the ~70 clients in this panel. History depth varies substantially by client, which is addressed in Limitations.

Features (all computed from March 2026 or a fixed past date, never from the label window):

FeatureKnowable at decision time because…
impressions_marchGSC impressions are logged as they happen; complete by month-end.
avg_positionSearch position is recorded daily, fully observed by month-end.
content_age_daysDerived from a fixed past creation date.
days_with_ga4Counts already-passed days with analytics available, not future behavior.

Label. is_declining = 1 if a page's April 2026 impressions fell below its March 2026 impressions, else 0. This is a future-window outcome label, not a reproduction of any current-window product bucket.

Baseline. A transparent hand-written rule: flag a page if content_age_days ≥ 180 AND impressions_march ≥ 500, scored by traffic volume among qualifying pages.

Models. Logistic regression (readable, linear) and random forest (non-linear, ensemble), both with class_weight="balanced" and random_state=42 fixed for reproducibility.

Validation design. A client-grouped split (GroupShuffleSplit, 75/25) ensures no client's pages appear in both train and test — the realistic scenario, since the model must generalize to clients it has limited history with, not memorize client-specific quirks.

Leakage checks performed: confirmed no product decision flags, no trend_direction/trend_pct (label-derived fields) in any feature; confirmed no preprocessing was fit on the full dataset before splitting; and directly demonstrated the cost of skipping this discipline — see Results.

Results

Precision@50 (of the top 50 flagged pages, how many were actually declining) on the held-out test set:

MethodPrecision@50
Baseline rule (stale + visible)0.500
Base rate (random guessing)0.578
Logistic regression0.660
Random forest0.700

Client-grouped split, March 2026 features → April 2026 label, n as described in Data.

Two findings are worth highlighting. First, the baseline rule performed below the base rate on this split — a genuinely humbling result showing the hand-written threshold missed most of the true positives in this panel, more than it caught. Second, and central to this paper's methodology point: the same random forest model scored 0.900 under a naive random train/test split — a full 0.200 higher than its honest, client-grouped score of 0.700. That gap is not noise; it is client-identifiable signal leaking across the split, exactly the failure mode a grouped split exists to prevent.

Feature importance (random forest): avg_position (0.366) was the strongest driver, followed by content_age_days (0.287) and impressions_march (0.284), with days_with_ga4 contributing little (0.063) — directionally sensible, since search position plausibly matters more to future traffic than raw volume or staleness alone.

Limitations & Honest Framing

  • This is decision-support, not causal: a page flagged as high-risk is a candidate for review, not proof that refreshing it will recover its traffic. No experiment or matched control was run to test that causal claim.
  • Single snapshot: results are based on one month-to-month window (March→April 2026); seasonal effects specific to this period have not been tested against other months.
  • Unbalanced panel: client history depth varies substantially; clients with little history are under-represented, and results may not generalize evenly across all client types.
  • Score formula limitation: within the qualifying baseline group, ranking is driven by raw traffic volume alone and does not weigh search position — a real gap a learned ranking model closes only partially, since the model's own score also does not explicitly optimize rank ordering beyond classification probability.
  • A closely related residual risk: content_age_days, the second-most important feature, may partly encode a training-split-specific pattern rather than a fully stable signal — three concrete false-positive cases in development work shared this profile (young, well-positioned, high-confidence-but-wrong predictions), suggesting some caution before treating this feature's contribution as fully generalizable.

Ranked Recommendations

Pages are scored and assigned one of three reason codes, each mapped to a suggested action for human review — never an automatic edit:

Reason codeSuggested actionWhen it fires
stale_high_valueReview for refreshAge ≥ 365 days and impressions ≥ 500
aging_visible_pageReview for refreshAge ≥ 180 days and impressions ≥ 500
visible_low_rankReview for CTR/intent fixImpressions ≥ 500 and average position > 10

Human review is required before any action, checking specifically: whether the page was recently updated outside the logged staleness field; whether a sibling page may be absorbing the same demand (consolidation, not decline); and whether the reason code matches what a reviewer actually sees on the page.

What must never be automated: no page should be auto-refreshed or auto-published from this output alone; FlyRank's own product decision flags must never be fed back into this model as features; and no external claim should use causal language ("this will improve traffic") — only decision-support language ("this page is a candidate worth reviewing").

Monitoring triggers: a material shift in the client mix, a drop in Precision@50 when re-scored on a new month against the 0.700 baseline established here, or a sharp change in how many pages clear the staleness/visibility thresholds each month, would each indicate the model or thresholds need revisiting.
